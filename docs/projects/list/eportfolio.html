About the project

BAA1028 Workflow & Data Management is the module that asks students to demonstrate, in a single deliverable, how reproducible workflows, version control discipline and structured data management are actually applied in practice. The deliverable is this ePortfolio: a publicly hosted website built from raw markup and styling rather than a CMS, version-controlled in Git, deployed automatically to GitHub Pages, and structured around data files that the page builds itself reads at render time.

I came into this module with prior experience building websites in WordPress and Elementor Pro for freelance clients. WordPress hides almost everything that this module is about: there is no Git history, no build pipeline, no concept of structured frontmatter, no separation between content and presentation. Switching to Quarto for this project meant doing all of those things explicitly, in code, for the first time. That gap between “I can build a website” and “I can build a reproducible web project” is precisely what BAA1028 is about, and it is what this page sets out to demonstrate.

NoteWhy this page is different from the other project pages

Every other page in this portfolio describes work that happened elsewhere and reproduces selected exhibits as Plotly charts. This page is meta: the project being described is the website you are reading, and the charts below analyse the actual repository at github.com/alekslupa/alekslupa.github.io. The data is generated by a small Python script (scripts/generate_repo_stats.py) that walks the Git history and the file tree, writes results to four CSV files in data/, and the page reads those CSVs at render time. That separation between data generation and presentation is itself a workflow choice the module is graded on.

1. The build pipeline

The pipeline is the most important artefact of a Workflow & Data Management project. Every change to this site flows through the same six stages, in the same order, every time. There is no manual upload step, no FTP, no copy-paste of HTML into a CMS. A commit triggers a render and a deployment, and the live URL is whatever the render produced.

The decision worth flagging is the output-dir: docs configuration in _quarto.yml. GitHub Pages can serve from either the repo root or a /docs folder; choosing /docs keeps the source .qmd files separated from the rendered HTML. The repo therefore has a clean split between authored content (the .qmd files, the data/ CSVs, the assets/ images, the styles.scss file) and rendered output (the docs/ directory). When something breaks on the live site, that split is what makes it possible to reason about cause and effect: either the source is wrong, or the render produced something different from the source.

2. Information architecture

The site is organised around a single principle: every project is a .qmd file in projects/list/ with structured frontmatter. The frontmatter is what the listing pages, the landing page Recent Posts and the individual project pages all read from. There is no duplication of titles or dates anywhere in the codebase. If a project’s title changes, it changes in one file and propagates to every page that references it.

The choice that matters most for Workflow & Data Management is treating YAML frontmatter as structured data rather than as decoration. Every project page declares its title, subtitle, date, image, categories and description in the frontmatter. Quarto’s listing engine then treats projects/list/*.qmd as a database table. Adding a new project becomes a single-file operation: ship the .qmd, the listing pages update on next render. This is the inverse of the WordPress workflow I started with, where adding a new project meant clicking through five admin screens and copy-pasting the title into three places.

3. The repository, in numbers

Below this point, every chart is generated from real data. The four input CSVs are produced by scripts/generate_repo_stats.py, which walks the Git history and the file tree and writes to data/. The page reads those CSVs at render time. None of the figures below are estimates.

Commit volume is a useful workflow signal. Long flat periods between work sessions are normal for a part-time student project; what matters is that within each work session the commits are reasonably granular rather than monolithic dumps. Squashing the entire ePortfolio into one giant commit at the end would render the Git history useless for any examiner who wanted to see how the project actually evolved.

4. SCSS growth: a workflow signal

A single styling file (styles.scss) handles the visual language of every page. Tracking how it has grown over the project’s lifetime is a useful proxy for one specific kind of progress: the steady accumulation of design decisions. Each touching commit either added a new component (.ab-skill, .fg-career__card, .hp-recent etc), refined an existing one, or fixed a bug.

Code 
import pandas as pd
import plotly.graph_objects as go

scss = pd.read_csv("../../data/scss_growth.csv", parse_dates=["date"])
scss = scss.sort_values("date").reset_index(drop=True)
scss["commit_n"] = range(1, len(scss) + 1)

fig = go.Figure()

fig.add_trace(go.Scatter(
    x=scss["date"],
    y=scss["lines"],

    marker=dict(size=7, color="#1e7e34", line=dict(color="white", width=1)),
    fill="tozeroy",
    fillcolor="rgba(30,126,52,0.10)",
    hovertemplate="<b>%{x|%b %d, %Y}</b><br>%{y} lines<br>commit %{customdata}<extra></extra>",
    customdata=scss["commit"],
))

fig.update_layout(
    height=400,
    margin=dict(l=20, r=20, t=20, b=30),
    paper_bgcolor="rgba(0,0,0,0)",
    plot_bgcolor="rgba(0,0,0,0)",
    font=dict(family="Inter, sans-serif", color="#1a1a1a"),
    xaxis=dict(title="Commit date", showgrid=False),
    yaxis=dict(title="styles.scss line count", showgrid=True, gridcolor="#eee"),
    showlegend=False,

fig.show()

A note about what this chart does and does not show. It shows the size of the file over time, not the quality of the code in it. SCSS that is large and well-organised is fine; SCSS that is large and chaotic is not. The qualitative judgement requires reading the file. The quantitative trend gives an accurate impression of effort distribution: the styling work accumulated over many short sessions rather than landing in one or two giant commits at the end.

The shape of this chart matters more than the absolute numbers. A healthy repo for a single-author web project should show one or two structural files (a stylesheet, a config) at the top, followed by content files that received roughly proportional attention. A pathological shape would be one file at 80 edits and everything else at 1, which would suggest the project was actually one page being rebuilt repeatedly. The actual shape here matches the healthy pattern.

What I was responsible for

Information architecture
Designed the site structure as a single-source-of-truth model: project pages declare their metadata in YAML frontmatter; listing pages query that frontmatter. No duplication, no manual sync.
Build pipeline and deployment
Configured Quarto with output-dir: docs, set up GitHub Pages to serve from the docs folder, established the local render-preview-commit-push workflow that every change flows through.
Visual language
Custom SCSS with no reliance on Quarto theming defaults. Single stylesheet of approximately 2,400 lines covering typography, components, dark mode, responsive breakpoints.
Reproducible analytics
Wrote scripts/generate_repo_stats.py to extract real metrics from the Git history and file tree. The script writes CSVs into data/, and this page reads from those CSVs. Data generation and presentation are separated.

Reflection

This was the project that most directly demonstrated the gap between “I can build a website” and “I can build a reproducible web project”. Coming from a WordPress freelance background, I underestimated how much of the cognitive load of web development WordPress hides. Quarto, Git and GitHub Pages each force decisions that WordPress makes invisibly. None of those decisions are individually difficult, but they all have to be made explicitly, in code, and they all have downstream consequences. Choosing output-dir: docs is a one-line decision that determines what the deploy URL serves. Choosing to centralise styling in a single SCSS file means the visual language is consistent but also means the file becomes a bottleneck. Choosing YAML frontmatter as the project metadata format means listing pages are automatic but also means every project must conform to the schema.

The decision I am proudest of is the one that produced this page. Every other project page in the portfolio describes work that happened elsewhere and reproduces selected exhibits as Plotly charts. For the ePortfolio page itself, that approach would have been circular: the project being described is the website hosting the description. Instead, the page reads real data from the actual repository and analyses itself. The CSV-generation script (scripts/generate_repo_stats.py) walks the Git history and the file tree once, writes its outputs to data/, and the page reads from those CSVs at render time. The separation between data generation and presentation is itself the workflow pattern the module is teaching, and applying it to the page that describes the module’s deliverable felt like the right way to demonstrate understanding rather than just describing it.

The honest limitation is that the workflow shown on this page is overkill for a single-author static site. A team-of-one editor running one repo with one deployment target does not strictly need a separate data generation script, an explicit pipeline diagram, or a documented information architecture. The reason to do all of those things anyway is that they are the same patterns that scale to projects where the overkill becomes underkill quickly. Treating a small project with the workflow discipline of a large one is cheap; the inverse is expensive. That generalisation is what I want to take out of this module into whatever team-based analytics work I end up doing after graduation.

A second honest note: this is the first project I have built without any visual builder in the loop. The quality of the result is genuinely the result of code I wrote myself, with the help of AI tools (Claude, Gemini, Grammarly) for structural suggestions, debugging and proofreading. Every architectural decision is mine; every line of SCSS is either written or directly reviewed by me; every Plotly chart on this page is generated from a real CSV produced by my own script.
